# Job App Toolkit

A Firefox WebExtension (Manifest V2) for job application workflows. Ships **Form Filler** and **Site Settings**, with the architecture in place for more.

## Export / Import

- **Backup / restore** — the popup footer's *Export data* button downloads every module's configuration as `job-app-toolkit-export-YYYY-MM-DD.json` (pretty-printed JSON): each module's sync payload plus its `browser.storage.local` user data. The popup's *Import data* button opens a persistent extension tab, where a JSON backup can be selected and validated without the toolbar popup closing underneath the native file picker. After confirmation, it overwrites the current configuration for the modules in the file and reports a clear success, total-failure, or partial-success status; partial and total failures name the affected module(s) and include a shortened safe error summary. The "Include API key" checkbox is off by default, so the form-filler API key only travels when you opt in; regenerable caches (Glassdoor ratings, people-search companies) are never exported. Form-filler profiles travel in the export's `local` object (`jtk-form-filler-profiles`); an old export that carries profiles inside the sync `data` object imports unchanged — they land in local storage and are stripped from sync. No new permissions needed.

## Form Filler

Save form fields to named profiles and autofill job application forms. Built for the hostile reality of job portals: same-origin iframes, dynamic fields, required-field asterisks, and verbose labels like "LinkedIn* This question is required".

### Features

- **Profiles** — save fields into named profiles and switch between them (e.g. one per job board).
- **Edit saved fields** — on the options page, use the single **Edit** button beside any saved field to update its title and value together in one modal; scalar values stay scalar, while multi-answer values are edited one answer per line (including an intentionally empty array). Saving both fields uses one profile persistence write.
- **Fill page** — fills every field it can from the active profile, never overwriting data already present.
- **Per-question buttons** — on whitelisted sites, every form question gets one in-page save (floppy-disk) / up-arrow fill button set, styled like Site Settings'. The set is anchored to the question's title (legend, label, or heading; the field itself when no title exists), and a question with several options — a checkbox group, same-named radios, or a `<select multiple>` — gets a single set for the whole group rather than one per option. The up-arrow button fills the question from the profile even when it already has a value. Buttons render in the top document **and** in same-origin form iframes the content script never reached, so portal forms get them even when Firefox skips frame injection.
- **Wrong-autofill corrections** — after any autofill (fill page, the per-question up-arrow button, or *Autofill this field once*), a small × appears beside the field for a few seconds — on any site, not just whitelisted ones. Clicking it clears the field and marks the profile-entry ↔ field pairing as incorrect, so future autofills skip it everywhere; an Undo toast (60s) restores the value and removes the mark. Corrections are global and keyed on the same normalized label identity matching uses — not raw name/id, which job sites hash — so they transfer across sites, and a field with a genuinely different label is unaffected (a correction can still intersect an unrelated question sharing a generic option norm like "yes"; the options page's *Clear all* is the escape hatch). An excluded pairing is skipped by fill page, the per-field fill button dims with a "Skipped (marked incorrect)" tooltip and toasts on click, and *Autofill this field once* reports an error; AI answers are unaffected.
- **Page templates** — save all fields on a page as a named snapshot via the *Save page template* context-menu action (inside the *Save fields* submenu). A naming dialog collects a name, then the page's field shape (ordered normalized question identities) and current values are persisted to `browser.storage.local`. When you next click *Autofill page* on a page whose field shape matches exactly, the saved values overwrite every field positionally — the i-th saved entry fills the i-th question group, including clearing fields where the template value is empty. This is a deliberate full override, unlike normal profile fill which never overwrites existing data. Templates are matched by field shape (not by URL), so a template saved on one site fills a same-shaped page on another. Manage or delete saved templates on the options page under the *Page templates* section.
- **Multi-answer questions** — checkbox groups, same-named radio groups, and `<select multiple>` are recognized as one question and saved/filled as a unit. A multi-answer question stores the selected options as an array of labels (an empty array is a valid "nothing selected" save); a radio group stores the checked option as a single value; a lone checkbox keeps its historical checked/unchecked encoding. Filling a stored multi-answer question is a full override — the stored options are selected and every other option is deselected. Radios are fillable like any single-answer field.
- **Section-header titles** — a saved question's title/key never comes from a section header (a heading like `<h2>Employment History</h2>` above several fields, or a shared fieldset legend covering multiple questions): an unnamed field whose only nearby title is a section header is skipped rather than saved under it (its placeholder or aria-label wins when present), and several checkbox/radio questions inside one fieldset are saved as separate questions, each under its own name/id. Previously-saved entries keyed by a section header still fill — the header text stays in the match-candidate list.
- **Button sites** — the whitelist of domains that get per-question buttons is managed on the options page; filling a page from the popup, options, or context menu auto-adds that domain. Each entry also covers its subdomains (so `acme.example` covers `jobs.acme.example`).
- **Add current field** — popup quick action that captures the focused field's name and value.
- **Debug logging** — an "Enable debug" toggle on the options page mirrors every Form Filler toast to the page console (in addition to the in-page toast), and mirrors each Ask AI stage (capture, job-description source, prompt sections, generate/judge/retry timings, fill) under a shared flow id — console only, never as extra toasts. Useful for diagnosing button placement, matching, and AI-answer flows.
- **Add all fields** — collects every filled-out field on the page in one go.
- **Context menu** — right-click any form page for *Autofill page*, *Autofill this field once* (fills just the right-clicked question from the profile, without whitelisting the domain), *Answer with AI*, and a *Save fields* submenu containing *Add all fields* and *Save page template*; the per-question actions also live in the in-page buttons.
- **Keyboard shortcut** — press **Ctrl+Alt+F** to run *Autofill this field once* on the focused field in the active web tab. The shortcut also checks available frames, so a focused same-origin form iframe can be filled without a context-menu target.
- **Options page search** — filter saved fields with a percentage-scored match, highlighting green by match quality; multi-answer fields also match on any of their saved options.
- **AI answers** — right-click a text field and choose *Answer with AI*: the field's label becomes the question, your saved experience/project entries become the background, and on supported job boards — Ashby and Wellfound postings, plus any MyGreenhouse ("Quick Apply with MyGreenhouse") application — the posting's job description is pulled in automatically so answers can reference the role; a model writes an answer that respects the field's character limit and single-line/multiline nature, then fills it in (overwriting). Each answer is self-checked — deterministic rules, then a strict LLM judge — with one automatic corrective retry, and a spinner sits on the field while the AI works. Works with any OpenAI-compatible endpoint — OpenAI, Groq, Ollama, LM Studio, and more — configured on the options page; the API key and your background entries are stored locally and never synced, and the agent's instructions (tone/format rules) are editable on the options page with a reset-to-default.
- **Application tracking** — on whitelisted sites, submitting a form is logged automatically: the module watches submit-capable controls (submit/image inputs, submit buttons, typeless in-form buttons, and JS buttons whose text reads like a progression action — "Submit", "Apply", "Continue", "Save & Continue", …; never anchors or Cancel/Back/Delete) and reports the top frame's URL, the page title, and a best-effort company (from a company/employer/organization field, else the job posting's structured data (JSON-LD `hiringOrganization`), else the "at Company" phrase in the page title, else the page's `og:site_name`) before the page navigates away — fire-and-forget, no user-visible effect. A repeat submission of the same URL is silently dropped, re-submitting the same job refreshes its date, and a new application starts at "applied". Open **Application History** from the popup quick actions or the options page's button to see the list — newest first, or sorted by company A–Z with empty companies last; a search box filters live by job title, company, or URL. Set each entry's stage from the standard ladder (applied → initial interview scheduled → … → offer accepted → rejected; a previously-set custom stage is preserved in the dropdown), edit company, job title, and URL in one modal (so auto-extraction mistakes can be corrected), open the posting, or delete the entry (with a confirm prompt). Entries live in `browser.storage.local` (never synced) and are included in export/import.
- **Already-submitted warning** — when the current posting has already been recorded as submitted, Form Filler shows a red warning at the top-left for 3 seconds. URL matching uses normalized absolute URLs and ignores only the hash fragment; query parameters are preserved because they can contain the job identity.

### How matching works

Fields are matched against the profile in three passes:

1. **Exact** — normalized identity equals a field candidate.
2. **Contains** — one string is a substring of the other.
3. **Word overlap** — the shorter string's significant words (≥3 chars, stop words dropped) all appear in the longer one, so "personal website portfolio" matches "website or portfolio" while "legal first name" does **not** match "legal last name".

Normalization lowercases and strips anything that isn't a letter or digit, so required-field asterisks, dots, underscores and hyphens never interfere. Real element `name`/`id` attributes are saved verbatim; title-derived names are cleaned before storing.

### Drop-down fields

The module fills `<select>` fields and custom combobox widgets (e.g. React Select, which renders a hidden `<input role="combobox">` alongside a `<div class="select__single-value">` showing the selected option's label). For both, a saved value is matched against option `value` **and** visible label; if no exact match exists, the closest option by word-overlap is chosen (same fuzziness used for field matching), and if none clears a threshold the field is skipped rather than filled with a wrong answer. Placeholder options ("Select...", "— Choose —", etc.) are never matched. The page-wide **Fill page** flow never overwrites a drop-down that already shows a real selection — the visible value is read back from the widget and tested against placeholders so pre-selected fields are left alone.

### iframe handling

Job portals render forms in (same-origin) iframes that Firefox does not always inject content scripts into. The module:

- Marks each document the content script runs in (`data-jtk-injected`).
- Walks same-origin iframes directly via `contentDocument`, skipping already-marked frames.
- Falls back to a **force pass**: when per-frame messaging finds nothing, the background asks the top frame to walk even marked iframes.
- Renders the per-question button sets into this document **and** every unmarked same-origin form iframe (a frame with its own script renders its own buttons); a 2-second re-scan poll catches form iframes that appear after the initial scan.
- The **Ctrl+Alt+F** shortcut sends its no-target fill request to each available frame so the content-side active-element fallback selects the focused field; frames where Firefox did not inject the content script cannot respond.

### AI answers

Right-click a text field on any form and choose **Answer with AI**. The module captures the field — its label (or name/id) becomes the question, its `maxlength` a hard limit — builds a prompt from the **AI background** entries on the options page (one per experience or project) and, on supported job boards, the posting's job description, then sends it to an OpenAI-compatible `chat/completions` endpoint. Ashby (`jobs.ashbyhq.com/<org>/<uuid>` and `…/application`) is matched by URL: the description comes from Schema.org `JobPosting` JSON-LD on the page (or a short background fetch of the posting URL if the live DOM miss). Wellfound (`wellfound.com` or `www.wellfound.com`) is matched by either `/jobs/<numeric-id>-<slug>` or `/jobs?job_listing_slug=<numeric-id>-<slug>` (with an optional trailing slash and other query parameters); the live DOM's `#job-description` is preferred and converted to capped plain text, then the background makes a credentialed fetch using the same selector and uses `JobPosting` JSON-LD only as a fallback. MyGreenhouse applications are detected by the server-rendered "Quick Apply with MyGreenhouse" button class — never by URL, so any company domain and embedded application iframe works — the background probes the right-clicked frame and the top frame, uses the description from whichever holds it (`.job__description` or `JobPosting` JSON-LD), and falls back to Greenhouse's public board API (`boards-api.greenhouse.io/v1/boards/<org>/jobs/<id>`, org + job id derived from the DOM) when neither does. A small spinner sits at the top-left of the field while the AI works. Before filling, the answer is self-checked — first against the field's constraints (empty, over `maxlength`, newlines in a single-line field), then by a strict LLM judge — and a failed check triggers one corrective retry that feeds the critique back to the model; a judge error never blocks a usable answer. Each call is capped at 60 seconds and the whole flow at 90, so a dead endpoint can't leave the spinner hanging: you get a clear "AI answer timed out" toast instead. The answer is truncated to fit the field and filled in, overwriting whatever was there; single-line inputs are asked for a short, one-sentence answer, and the page title is passed as weak context so answers can be tailored to the company.

Endpoint and model are configured on the options page and sync across devices; the AI agent's instructions — the tone and format rules it follows when answering — are editable there too, and blanking them restores the built-in default. The API key and the AI background entries are stored in `browser.storage.local` and never synced — Firefox's `storage.sync` quota is a hard 100 KiB that bulky entry text would blow through (and it cannot be raised by any permission).

### Storage

Single `jobAppToolkit` key in `browser.storage.sync` → `{ modules: { "form-filler": { active, activeProfile, whitelist, aiEndpoint, aiModel, aiInstructions, debug } } }`. Profiles are **not** in the sync payload: they live in `browser.storage.local` under `jtk-form-filler-profiles` (`{ "<name>": { fields: { … } } }`) because they are the bulkiest payload and would blow the fixed 100 KiB sync quota. Every reader goes through a helper that prefers the local copy and falls back to a legacy sync copy: the background wraps module-data access in `readFormData`/`writeFormData` (a write always persists profiles to local first, then passes `profiles: undefined` so `setModuleData` deletes any stale sync copy), and the content script's `loadConfig` and the options page read local-first with the same fallback. A non-empty legacy sync copy found on first access is copied to local, verified by read-back, then stripped from sync; if the sync strip hits the quota error it is retried by the next write. `debug` (boolean, default false — the "Enable debug" toggle on the options page) mirrors every Form Filler toast to the page console and mirrors Ask AI stage logs there too (`form-filler:aiDebugLog`; never as toasts). `whitelist` is the array of hostnames (lowercase, no `www.`) that show per-question buttons; an entry matches its exact hostname or any of its subdomains (never a bare TLD). Each profile's `fields` maps a field identity to `{ value, label, type }`, where `value` is `string | string[]` — a scalar string for single-answer fields (text inputs, selects, radio groups, lone checkboxes) and an array of the selected options' labels/values for multi-answer questions (checkbox groups, `<select multiple>`), with `[]` a valid "nothing selected" save — and `type` is the coarse control type captured at save time (`text`, `textarea`, `checkbox`, `radio`, `select`, or `""` for legacy entries). Matching is type-aware: an entry whose `type` is set only matches page elements of that type, while an empty/missing `type` matches any element (backward compatible with old profiles). The type is editable per field on the options page. Legacy bare-string entries (a value stored directly under the key) still load and fill. `aiEndpoint`/`aiModel` configure the AI call; `aiInstructions` is the editable instruction block sent as the system prompt (blank falls back to the built-in default). The AI background entries (`aiContext`, the array of `{ title, body }`) and the API keys are **not** in sync storage — they live in `browser.storage.local` under `jtk-form-filler-ai-context` and `jtk-form-filler-ai-keys` (a list of `{ id, name, key }` with the selected key's id in `jtk-form-filler-ai-active-key`), because entry text is bulky and the sync quota is a fixed 100 KiB that no permission can raise. A legacy `aiContext` still sitting in module data is migrated to local on the next options-page load, and its stale sync copy is dropped so it stops occupying the quota; the legacy single API key (`jtk-form-filler-ai-key`) is likewise migrated into the key list as a "Default" entry on the next options-page load and then removed. Page templates (`jtk-form-filler-templates` in `storage.local`) store `{ "<id>": { name, shape, fields, savedUrl, createdAt } }`, where `shape` is the ordered array of normalized field identities and `fields` is the matching ordered array of `{ identity, value, fieldLabel }`. Wrong-autofill exclusions (`jtk-form-filler-exclusions` in `storage.local`) store `{ "<signature>": { profileKey, fieldNorms, ts } }`, where the signature is `profileKey + \u0000 + sorted fieldNorms \u0001`.

## Site Settings

Per-site company controls for job search listings. Ships a LinkedIn adapter that adds two buttons — `★` highlight and `⊘` block — to each company name on `/jobs/search` results, and a second adapter that surfaces each person's current employer as a new line under their title on `/search/results/people/`.

### Features

- **Block** — hides every posting from a company. Applied as both a class and an inline `display:none !important`, so the hide survives LinkedIn's SPA re-renders (React rewrites `className` on card nodes, which would silently drop a class-only hide).
- **Highlight** — tints matching postings amber for quick scanning.
- **Mutually exclusive** — blocking a company clears its highlight and vice-versa.
- **Title keywords** — a per-site keyword list; any posting whose title contains one of the keywords is hidden like a blocked company (matching is case/punctuation-insensitive substring matching on the job title).
- **Filter button** — every job title gets a small funnel button (styled like the block/highlight buttons) that opens an in-page prompt prefilled with that posting's title; confirming adds the keyword to the filter list.
- **Hide applied** — an options toggle that hides postings LinkedIn marks as already applied to. Detection uses centralized applied-markers selectors plus a guarded short-badge text fallback, so titles/companies like "Applied Scientist" or "Applied Materials" never trigger it.
- **Glassdoor ratings** — an options toggle (off by default) that adds a small `★ 4.4` badge beside each company name on `/jobs/search`. The badge shows the company's overall Glassdoor rating with the review count on hover; clicking it opens the company's Glassdoor page in a new tab. Ratings are fetched in the background, cached aggressively (90 days on success, 7 days on failure), and silently skip hidden cards. A failed fetch shows a `?` badge instead — click it to retry.
- **People-search company** — an options toggle (off by default) that adds a small line under each person's job title on `/search/results/people/` showing their current employer. The company is scraped from the **top card** of that person's `/in/<vanity>/` profile by the background script (the parser targets a unique class on the company line in the top card); results are cached in `browser.storage.local` for 7 days on success, 1 hour on failure. A company is requested the first time a card scrolls into view (IntersectionObserver, lazy), and subsequent visits are instant cache hits. A failed fetch (private profile, 404, auth wall, parse miss) silently drops the line — no permanent `?` placeholder — and the next request retries after the failure TTL. The options page exposes the cache size and a Clear-cache button.
- **Undo toast** — blocking raises a toast with an Undo button; tapping it unblocks and restores the card immediately.
- **Options page** — global on/off toggle, Blocked and Highlighted company lists, the Hidden title keywords list, a Hide-applied switch, the Show Glassdoor ratings toggle, and the Show company on people-search toggle (with Clear cache).
- **Sync + live** — per-site lists and the two rating toggles live under `sites.linkedin` in sync storage; the rating caches live in `browser.storage.local` and changes apply to all open tabs instantly via `storage.onChanged`.

### How it works

- **Adapter pattern** — `currentAdapter()` matches the page (LinkedIn: `location.pathname` starts with `/jobs/search`) and exposes `findJobCards()` / `companyFromCard()`; adding a site means adding another adapter.
- **Scan + observe** — cards are rescanned on load, storage change, a 2s poll, and DOM mutations (`childList` *and* `class` attribute changes, so re-renders re-apply within ~150ms).
- **Click safety** — LinkedIn job cards are fully clickable, so button clicks call `preventDefault()`/`stopPropagation()` and the buttons are raised with `z-index`; otherwise clicking `⊘` (or the title filter funnel) bubbles into the card's own navigation handler and the hide is undone. The filter prompt is an overlay on `document.body`, outside any card, so its events never reach the card handlers. The Glassdoor badge uses the same z-index + stop-propagation pattern and opens the company page in a new tab on click.
- **Glassdoor rating pipeline** — when the toggle is on, the content script debounces (250 ms) the unique on-screen company names and sends one `site-settings:glassdoor:getRatings` batch to the background. The background resolves each company against `api.glassdoor.com` (the API host is not behind Cloudflare — no cookie, no cold-start, no glassdoor tab required) via the typeahead → BFF → Overview-HTML pipeline, throttled (≥ 2 s gap, 15 per session) and cached (90 d success, 7 d failure). As each fetch completes, the background broadcasts `site-settings:glassdoor:updated` and the badge appears in-flow. A failed or zero-reviews result renders a `?` badge; clicking it sends `site-settings:glassdoor:retryRating` and the badge swaps to a spinner until the next broadcast resolves it. Cards that are already hidden (blocked company, title keyword, or hide-applied) are skipped entirely. Toggle off = zero requests and no badges.

### Storage

`{ modules: { "site-settings": { active, sites: { linkedin: { blockedCompanies: [], highlightedCompanies: [], titleBlockedKeywords: [], hideApplied: false, showGlassdoorRatings: false, showPeopleSearchCompany: false } } } } }` plus two `browser.storage.local` keys: `jtk-site-settings-glassdoor` → `{ [normalizedName]: { ok: true, rating, count, countText, pageUrl, employerId, schemaVersion, fetchedAt } | { ok: false, reason: "blocked" | "fetch_error" | "no_match" | "parse_error" | "no_reviews", schemaVersion, fetchedAt } }`, and `jtk-site-settings-people` → `{ [vanity]: { ok: true, company, schemaVersion, fetchedAt } | { ok: false, reason: "not_found" | "auth_wall" | "fetch_error" | "parse_error", schemaVersion, fetchedAt } }`. Companies and keywords are stored verbatim and matched case/punctuation-insensitively; blocked and highlighted are mutually exclusive per company, the title keyword list is an independent filter (a match hides the card regardless of company state), `hideApplied` is a per-site on/off that hides applied-marked cards like a block, `showGlassdoorRatings` (default `false`) gates the optional Glassdoor rating badge on `/jobs/search`, and `showPeopleSearchCompany` (default `false`) gates the people-search company line on `/search/results/people/`. The Glassdoor rating cache is keyed by normalized company name; the people company cache is keyed by lowercased vanity URL. Both caches live in `storage.local` (the sync quota is a fixed 100 KiB). For the Glassdoor cache: `count` is the K/M-abbreviated review count (e.g. `"70.7K"`); `countText` is `count + " reviews"`. For the people cache: a positive entry's `company` is the current employer's display name (taken from the current-employer line in the profile's top card). `schemaVersion` lets future fetcher changes evict stale entries automatically.

## Architecture

- `core/` — framework: storage, background router, UI helpers, popup, and the shared content runtime.
- `core/content.js` — content-side runtime (module-active cache, toast with optional action button) exposed as `window.jobAppToolkit.content`. Must be listed **before** module content scripts in `manifest.json`.
- `modules/<id>/` — self-contained modules registered via `window.jobAppToolkit.registerModule(...)`. Messages are namespaced (`form-filler:*`, `site-settings:*`), and context-menu items are dispatched to every module, which filters its own.
- `manifest.json` — lists background scripts and content scripts; all module files are wired in here.

## Roadmap

Ideas discussed but not yet built:

- **Better field-type coverage** — e.g. the select-with-linked-free-text combo pattern found on some job boards.
- **Legacy profile migration** — existing stored profiles may not have survived the storage restructure; add a migration path.
- **Smoke-test suite** — promote the jsdom harnesses (`/tmp/opencode/jtk-test/`) into the repo as a regression suite.
- **Chrome/Manifest V3 support** — currently Firefox-only (MV2).
- **AI answer refinement** — an interactive feedback loop or interview-style chat to clarify and refine generated answers (today only the automatic self-check retry exists).
