# Architecture

Firefox WebExtension (Manifest V2). Two modules ship today (**Form Filler** and **Site Settings**); the framework supports more.

## Layout

- `core/` — framework.
  - `storage.js` — per-module store under one `jobAppToolkit` sync key, active flags, legacy migration. Bulky per-module payloads live in `browser.storage.local` instead (form-filler AI background entries, API key) because the sync quota is a hard 100 KiB.
  - `background.js` — module registry, shared context-menu root, message router (passes the real `sender` to modules), toast relay, last-web-tab tracker, activity broadcast, and export/import orchestration (`jtk:exportData` collects `{ data, local }` from every module into an envelope; `jtk:importData` validates and restores it).
  - `popup.{js,html,css}` — module list, activity toggle, quick actions, open-options, plus an export/import footer: *Export data* (with an "Include API key" checkbox) downloads the envelope as pretty-printed JSON via a Blob URL + `<a download>`, and *Import data* reads a hidden file input (.json/text) through a confirmation modal.
  - `ui.js` — shared status line + confirm/prompt modal for extension pages.
  - `content.js` — content-side runtime exposed as `window.jobAppToolkit.content`: module-active cache (`isModuleActive`/`refreshActive`) and a `showToast(text, action)` that renders an optional action button. Every content script loads it first.
- `modules/<id>/` — self-contained modules registered via `window.jobAppToolkit.registerModule(...)`.
  - `modules/form-filler/content.js` — field discovery, question grouping, 3-pass matching (exact → contains → word overlap), normalization, native value setters, checkbox/radio/select handling, same-origin iframe walk, capture/collect/fill handlers, in-page toast, and save/up-arrow per-question buttons (add to profile / fill from profile) rendered only on whitelisted hosts (full teardown when the module is off or the host isn't whitelisted). Fillable elements are partitioned into question groups by `discoverGroups`: single-answer controls stand alone; choice controls answering one question — same-named radios (grouped by `name`), checkbox groups, `<select multiple>` — group via the nearest `<fieldset>`/legend, then a shared title element, then a shared container holding 2+ choice inputs and a question title of its own (`classifyField`/`findSharedContainer`/`resolveGroupTitle`); a leftover lone checkbox stays a scalar field. Section-header titles never become question titles: a kind-aware pre-pass (`computeSectionHeaderTitles`) flags any title element that reads as covering >1 question — ≥2 fields with any single-answer resolver, or choice-only resolvers spanning ≥2 distinct non-empty `name`s — and suppression is two-sided. At resolution level `getTitleElement` returns null for a flagged element, so singles, shared-title grouping, and every `resolveGroupTitle` branch (fieldset legend, shared title element, shared container) never yield a section header; on the save side `saveFieldTitle`/`getHeaderLikeTextIfLocal` drop flagged header TEXT, so an unnamed field whose only nearby title is a section header falls through to its placeholder/aria-label or is skipped (never keyed by the header), while fill matching deliberately keeps the unsuppressed header text in the candidate list so legacy section-header-keyed entries (e.g. "Employment History") keep filling. A fieldset's multi inputs are bucketed per distinct non-empty `name` (one group per name plus a nameless remainder) — two checkbox questions under one legend save as two questions — and a post-pass clears any title element shared by ≥2 groups, re-keying those groups by element name/id and re-anchoring at the first input. Leftover multi fields that grouped by neither fieldset/title/container group by shared non-empty `name` before falling back to standalone. Each group gets ONE button set anchored at its question title element (`getTitleElement`: linked `label[for]`/parent label/aria-labelledby, then a header-like walk falling back to the `<fieldset>` legend), with the field itself as fallback — the anchor is the question title or the group's first field, never a shared container, so split questions can't collide on one set. Capture (`describeGroup`) saves singles as scalars, radio groups as the checked option's label/value, and multi-answer questions as an ARRAY of the selected options' labels/values (`[]` valid); fill (`fillGroup`) applies array values as a full group override — stored options selected, everything else deselected — while `fillPage` matches per-element but fills each group once. Buttons render into the top document and any unmarked same-origin iframe; the whitelist matches an entry's exact hostname or any subdomain; a 2s poll re-scans for late-loading form iframes. The AI flow reuses this field machinery: `form-filler:getAIFieldInfo` captures a right-clicked field's label/subtitle/maxlength/type (the subtitle is description-styled text near the question title, e.g. Ashby's `.ashby-application-form-question-description`, via `fieldSubtitle`), `form-filler:getJobDescription` reads JobPosting JSON-LD from the top document for Ask AI board adapters, `form-filler:fillAIField` writes the AI answer back through the same native value setters, and `form-filler:aiSpinner` toggles a field-anchored loading ring (its own `<style id="jtk-form-filler-spinner-styles">`, `position:fixed` from `getBoundingClientRect()`, rAF/scroll/resize tracking) while an answer is pending. The spinner's lifecycle is purely message-driven — teardown() deliberately never touches it, because the AI flow also runs on non-whitelisted pages where teardown fires every 2s. A max-age watchdog (`SPINNER_MAX_AGE_MS` = 100s) self-hides the ring if the hide message can never arrive (e.g. the background died mid-flight); the background normally hides it first at its 90s flow deadline.
  - `modules/form-filler/background.js` — module registration: popup quick actions, the `form-filler:addField` handler (values pass `isValidFieldValue` — a non-empty string, or an array whose elements are all non-empty strings; an empty array is valid, for a saved multi-answer question with nothing selected; the same check guards the focused-field capture), cross-frame collect/fill orchestration with force-pass fallback, and a page-level context menu (Add all fields / Fill page — the per-field menu items moved to the in-page buttons). Filling a page (popup, options, or menu) auto-adds its domain to the `whitelist`. An "Answer with AI" menu item (editable contexts) captures the field, optionally resolves a job description via a small board adapter registry (Ashby first: match `jobs.ashbyhq.com/<org>/<uuid>[/application]`, prefer top-frame `form-filler:getJobDescription`, else fetch the canonical posting URL and parse `JobPosting` JSON-LD; session-cached, fail-open), builds a prompt from the stored AI background entries plus that description, calls the configured OpenAI-compatible `chat/completions` endpoint, self-checks the answer (deterministic rules, then an LLM judge) with one corrective retry, truncates to the field's maxlength and fills it back in, with a spinner on the field via `form-filler:aiSpinner`. The whole AI section runs under a flow deadline (`aiTimeouts` — 60s per call, 90s total) that aborts in-flight calls through a shared `AbortController` and toasts a distinct "timed out" message (per-call endpoint abort vs flow deadline); the spinner never sits through the full worst case. Export/import hooks follow the same storage split: `exportData` returns the sync payload minus `active` and the legacy `aiContext` plus `jtk-form-filler-ai-context` from `storage.local` — the API key (`jtk-form-filler-ai-key`) only when `opts.includeApiKey` is set and a non-empty key is stored — and `importData` restores the payload, the active flag, and the local entries present in the export (a redacted export without the key leaves an existing stored key untouched).
  - `modules/form-filler/options.{js,html,css}` — profile management, search with %-match highlighting, and the "Button sites" whitelist editor (`whitelist` array of hostnames). Stored values render through `displayValue`: array values (multi-answer questions) join with ", " and show "(none selected)" when empty, scalars as before (legacy bare-string entries included); `entryNorms` makes every stored option of an array value searchable alongside the key/label. Also carries the AI answers config (endpoint, model, editable agent instructions — blank falls back to the built-in default — and the API key — kept in `browser.storage.local`, never synced) and the AI background entry editor (`aiContext` array of `{ title, body }`, also in `browser.storage.local`). An "Enable debug" toggle (`debug` in the sync module payload) mirrors every Form Filler toast — both the background-originated in-page toasts (tagged with the module id in the `jtk:showToast` message) and the content-side `toast()` helper output — to the page console while on, and mirrors each Ask AI stage to the page console via `form-filler:aiDebugLog` (never as a toast).
  - `modules/site-settings/content.js` — two page adapters and one driver per page: (1) `linkedinAdapter` matches `/jobs/search` and drives the block/highlight/title-keyword flow (scan cards, classify each as blocked/highlighted/normal via per-site lists, inject the `★`/`⊘` company buttons and the funnel title-filter button, observe mutations and re-scan on a 2s poll, hide blocked cards with class + inline `display:none !important`). Also renders the optional Glassdoor rating badge (`jtk-ss-gd` wrapper, in-flow next to the company name using the same block-vs-inline placement as the company buttons): when `sites.linkedin.showGlassdoorRatings` is on, the scan collects unique on-screen company names, debounces a single `site-settings:glassdoor:getRatings` request, and renders the badge from the batch response or from a `site-settings:glassdoor:updated` broadcast. Three badge states: success (`★ 4.4`, opens the Glassdoor profile in a new tab), retrying (CSS-only spinner while a `?`-click retry is in flight), and failed (`?`, click to retry). Hidden cards (blocked / keyword / applied) are skipped entirely and have their badge removed. (2) `linkedinPeopleAdapter` matches `/search/results/people/` and drives the company-line flow: each card's `role="listitem"` is scanned, the first `a[href*="/in/"]` link is the profile, the first text-row `p` with the standard class set is the title, the text column is the title's parent. When `sites.linkedin.showPeopleSearchCompany` is on, the driver inserts a `jtk-ss-ppl` wrapper below the title row (using the same class set as the location row, so it looks native) and registers it with an `IntersectionObserver` so a `site-settings:people:getCompany` request fires the first time the card scrolls into view. The wrapper starts in a `…` (pending) state and is replaced with the real company name when the `site-settings:people:companyResolved` broadcast lands. Toggle off → zero requests, all wrappers removed, IO disconnected. The two drivers share a teardown path: each has its own observer/wrappers/state, and `teardownDriverState(prev)` strips the previous driver's state when the adapter changes mid-session (e.g. user navigates from `/jobs/search` to `/search/results/people`).
  - `modules/site-settings/background.js` — `setCompanyState` / `addTitleKeyword` / `undoBlock` handlers; block raises a toast with an Undo action, keyword adds raise a plain confirmation toast. Also owns two background fetcher pipelines: the Glassdoor rating pipeline (per missing company: typeahead `searchsuggest/typeahead?source=GD_V2&version=NEW&rf=full&fallback=token` on `api.glassdoor.com` to get `{ employerId, suggestion }`, then a `POST` to `https://api.glassdoor.com/bff/employer-profile-mono/employer-reviews` with body `{ employerId, pageSize: 3, page: 1 }` parsed for `data.employerReviews.ratings.{overallRating, reviewCount}`; `reviewCount` runs through the `formatCount` helper for K/M display), and the people-search company pipeline (per missing vanity: a single `GET` to the person's `/in/<vanity>/` profile, parsed for the company `<p>` in the top card — the line identifiable by the `_08b5ea62` class, which is server-rendered and so present in the `fetch()` body). A zero-reviews Glassdoor BFF response is a valid "no rating" state — cached with `reason: "no_reviews"` and shown as a `?` badge. On Glassdoor BFF failure the pipeline falls back to the `api.glassdoor.com` Overview HTML and parses `.CompanyOverview_overallRating` / `.CompanyOverview_ratingCount`. The people-company parser has no fallback: a private profile / 404 / non-profile body returns `null` and the entry is cached as `parse_error` or `not_found` (the failure TTL is 1 h so a real profile that returns transiently empty is retried quickly). Both pipelines are serial (≥ 2 s gap); Glassdoor has a 15-per-session cap, people has no cap (the 2 s gap is the rate-limit safety). An `AbortController` abandons the in-flight request on background unload. Results are cached in `browser.storage.local` (`jtk-site-settings-glassdoor` keyed by normalized company name, `jtk-site-settings-people` keyed by lowercased vanity URL; Glassdoor: 90 d success TTL, 7 d failure cooldown; people: 7 d success, 1 h failure; both have `schemaVersion` for automatic eviction on fetcher changes). Each completion is broadcast to the originating tab via `browser.tabs.sendMessage`: `site-settings:glassdoor:updated` or `site-settings:people:companyResolved`. The `site-settings:glassdoor:retryRating` message evicts a single cache entry and re-queues the fetch (used by the `?`-badge click); the people-company flow has no manual-retry message — the next scan retries after the failure TTL, or the user can hit Clear cache on the options page. Both toggles are re-read on every request so a mid-session flip takes effect immediately without a background restart. A `site-settings:people:clearCache` message removes the people-company cache key. The export/import hooks are config-only: `exportData` returns the sync payload minus `active` with an empty `local` — the Glassdoor and people caches are regenerable derived data and never travel with an export — and `importData` restores the payload and active flag.
  - `modules/site-settings/options.{js,html,css}` — global toggle, Blocked/Highlighted company lists, the hidden-title-keywords list, the hide-applied switch, the Show Glassdoor ratings toggle (default off, persisted in `sites.linkedin.showGlassdoorRatings`), and the Show company on people-search toggle (default off, persisted in `sites.linkedin.showPeopleSearchCompany`) with a "Clear cache" button that fires `site-settings:people:clearCache` and shows the current cache size (successes + failures).
- `manifest.json` — MV2, permissions `storage`, `contextMenus`, `tabs`, `<all_urls>`, `unlimitedStorage` (so `storage.local` isn't capped at the default IndexedDB quota), and `*://*.glassdoor.com/*` (explicit cross-origin scope for the rating fetcher; the `<all_urls>` permission already covers it at runtime, but the explicit form makes the scope visible in the add-on manager). Content scripts run `all_frames` at `document_idle`; background loads `storage.js` → `background.js` → module background scripts. Site Settings content scripts are `["core/content.js", "modules/site-settings/content.js"]` for LinkedIn.

## Messaging

- `jtk:*` — core-reserved (getModules, setModuleActive, runQuickAction, openOptions, showToast, moduleActivityChanged, exportData, importData).
- `<moduleId>:*` — dispatched to the owning module's `handleMessage(message, sender, moduleApi())`; `sender` carries the originating tab/frame.
- Context-menu clicks are dispatched to every module, which filters its own menu ids.
- `jtk:showToast` accepts an optional `action = { type, label, payload }`; clicking the action button sends `type` back to the background (used by Site Settings' Undo). An optional `module` field (the originating module id) is forwarded to content scripts so a module can mirror its own toasts to the page console for debug.

## Key flows

- **Fill page / collect** — background gets frame ids via `tabs.getAllFrames`, sends per-frame messages, dedupes/merges results. When nothing responds, a "force" pass asks the top frame to walk even `data-jtk-injected` same-origin iframes directly. Choice controls are matched per-element (each group member also carries its group's question-title identities, so a title-keyed multi-answer entry finds the group) but filled once per question group: array entries fully override the group, radio entries check the matching radio, and mismatched shapes (an array on a radio group, a scalar on a real multi-answer question) are left untouched.
- **Fill field / add field** — the in-page save (floppy-disk) button sends `form-filler:addField` with `{ name, value, fieldLabel }` — for a multi-answer question `value` is the array of selected option labels — and the background validates it (`isValidFieldValue`), merges it into the active profile, and the content script toasts the result (the "Add Current Field" popup quick action still resolves the focused field across frames via `getFocusedField` → `document.activeElement` + `findFieldNear`). One button set per question group, tracked in a WeakMap keyed by the group's anchor (title element, shared container, or first input — re-scans update state instead of rebuilding; each document gets its own stylesheet) and rendered only when the module is active **and** the hostname (or a parent of it) is in the `whitelist`; the set is inserted next to the question title element when one exists, else after the group's first input, and the same-origin walk renders it into unmarked form iframes that lack their own content script. The up-arrow button matches the question against the active profile locally (the group's cleaned title/key plus every member input's own candidates, so legacy scalar entries keep matching) and fills the whole group unconditionally — arrays select exactly the stored options, radios check the matching radio — overwriting, by design.
- **Answer with AI** — the module's "Answer with AI" menu item (editable contexts only) sends `form-filler:getAIFieldInfo` to the right-clicked frame: the field's label/name becomes the question, any subtitle/description text near the question title (`fieldSubtitle`: description/subtitle/hint-styled nodes after the title element in its container, capped at 800 chars) is added as an "Additional context:" line, and its `maxlength` a constraint. On supported boards a job-description adapter then runs: Ashby matches `jobs.ashbyhq.com/<org>/<uuid>` and `…/application`, asks the top frame for `form-filler:getJobDescription` (JobPosting JSON-LD → plain text, capped at 10k chars), and on a miss fetches the canonical posting URL (strip `/application`) to parse the same JSON-LD; results are session-cached and fail-open so a miss never blocks answering. The background guards on a configured key/endpoint/model/background, toasts "Asking AI…", signals the spinner (`form-filler:aiSpinner` on the target field), then POSTs the prompt to the endpoint (`Authorization: Bearer`, `max_tokens`, 60s abort); the system message is the options-page "Instructions for the AI agent", blanking it restores the built-in default. The user message places an optional `Job description:` block (title + body) between Background and Question when one was resolved. When module `debug` is on, every stage is mirrored to the page console via `form-filler:aiDebugLog` (capture, job-description source, prompt section summary, generate/judge/retry timings with short previews, fill, total ms) — console only, never as extra toasts; the background console always logs the same stages. The answer is then self-checked before filling: deterministic rules (empty, over `maxlength`, newlines in a single-line field) via `runDeterministicChecks`, and when clean, a strict LLM judge (`JUDGE_SYSTEM`, 120 `max_tokens`, temperature 0, fail-open on error) via `buildJudgeMessages`/`parseJudgeResult`. Any failure triggers exactly one corrective retry that re-sends the prompt with the prior answer as an assistant turn and the critique as a follow-up user message (`buildRetryMessages`); the retry is re-checked deterministically (warn-only). The answer is then truncated to the field's maxlength (word-boundary cut) and written back via `form-filler:fillAIField`, which re-resolves the same field and overwrites by design; the spinner is hidden on every terminal path (API error, fill failure, success). The whole AI section runs under a flow deadline (`aiTimeouts`: 60s per call, 90s total) that aborts in-flight calls through a shared `AbortController`; the failure toast distinguishes a flow deadline ("AI answer timed out after 90 seconds.") from a per-call endpoint abort ("the endpoint did not respond"). The API key and the AI background entries live in `browser.storage.local` (never synced — the sync quota is a fixed 100 KiB); endpoint/model are synced and edited on the options page.
- **Application tracking** — on whitelisted pages the form-filler content script watches submit-capable controls — `input[type=submit|image]`, `button[type=submit]`, typeless `<button>`s inside a form, and JS `<button>`s whose collapsed text matches a progression regex (Submit/Apply/Continue/Save & Continue/…; anchors and Cancel/Back/Delete never match) — across the top document and every same-origin iframe. `ensureSubmitMonitor` (called per document from `scanPage`'s same-origin walk) attaches capture-phase click + submit listeners tracked in the `submitMonitors` map with a per-document 1 s `lastLogAt` double-fire guard; `teardown()` detaches exactly the listeners each frame attached. On a hit it fire-and-forgets `form-filler:logApplication { title, url, company }` before navigation: URL from the top frame (`window.top.location.href`, cross-origin fallback to the submitting document), title from the submitting document (fallback: top's), company best-effort from a company/employer/organization field, else the job posting's JSON-LD `hiringOrganization` (the employer as the ATS marked it up), else the "at Company" phrase in the page title, else the `og:site_name` meta, else "". The background merges entries in `browser.storage.local` under `jtk-form-filler-applications` (the sync quota is a hard 100 KiB, same pattern as the AI entries): identical non-empty URL → duplicate, no write/toast; same normalized title AND (both companies empty or normalized-equal) → refresh `appliedAt`, keep the original url; else push `{ id, title, url, company, appliedAt, stage: "applied" }` (`id` = base-36 `Date.now()` + random suffix) and toast "Application logged.". Messages: `form-filler:getApplications` → `{ ok, applications, stages }`, `form-filler:setApplicationStage { id, stage }` (any non-empty string; empty is a no-op), `form-filler:deleteApplication { id }`. The history page (`modules/form-filler/applications.{html,js,css}`, loading `core/storage.js` + `core/ui.js`) lists applications newest-first (or company A–Z, empty companies last), sets each row's stage — the predefined `APPLICATION_STAGES` ladder plus a previously-set custom stage, which round-trips on re-render — opens the posting via `browser.tabs.create` when the url is non-empty, edits the row's company label via `form-filler:setApplicationCompany { id, company }` (empty clears it, so the row falls back to the job title / "Unknown company"), and deletes behind a `ui.showConfirm` modal. The popup quick action "Application History" and the options page's "Application History" button both open the page. It's a plain MV2 extension page — directly reachable, so **no `manifest.json` changes needed**. The log travels with export/import through the module's `exportData`/`importData` `local` object.
- **Matching** — candidates in priority order (name, id, placeholder, linked/parent label, aria-label/-labelledby, header-like walk). Passes: exact identity, then contains, then word overlap (≥2 shared significant words). Choice controls additionally carry their group's question-title identities, so a title-keyed multi-answer entry resolves to the whole group.
- **Content script** — no-ops unless the module is active (cached flag refreshed on load + broadcast). Marks each document `data-jtk-injected="1"` so the iframe walk skips frames reached by per-frame messaging.
- **Export / Import** — the popup footer's *Export data* sends `jtk:exportData` with `includeApiKey` from the "Include API key" checkbox (default unchecked). The router asks every registered module for `{ data, local }` — via its optional `exportData(api, opts)` hook, else a fallback that exports the sync payload minus `active` with an empty `local` — and wraps the results in an envelope `{ format: "job-app-toolkit", version: 1, exportedAt: <ISO timestamp>, modules: { "<id>": { active, data, local } } }`. The popup pretty-prints it and downloads `job-app-toolkit-export-YYYY-MM-DD.json` from a Blob URL + `<a download>` (no new permissions). *Import data* opens a hidden file input (`.json`/text), parses the file (invalid JSON → "Not a valid export file."), and confirms with a modal before sending `jtk:importData`. The router rejects envelopes with a wrong `format`/`version` or a non-object `modules` ("Unsupported export format."), then imports sequentially — each `setModuleData` reads-modifies-writes the shared `jobAppToolkit` key, so parallel writes would lose updates: per module, the optional `importData(api, exported)` hook, else `setModuleData(data)` + `setModuleActive(active !== false)`; a module that throws is logged and skipped while the rest import. Form Filler exports its sync payload (minus `active` and the legacy `aiContext`) plus `jtk-form-filler-ai-context` from `storage.local` — the API key (`jtk-form-filler-ai-key`) only when `includeApiKey` is set AND a non-empty key is stored, and a redacted import leaves the stored key untouched. Site Settings exports only the `sites` config; the Glassdoor and people caches are regenerable derived data and are never exported.
- **Site Settings scan** — the driver selects a page adapter (`currentAdapter()`), finds cards via adapter selectors, and per card: matches the company name against the site's blocked/highlighted lists, the title against `titleBlockedKeywords`, and (when `hideApplied` is on) the card against applied-markers detection; applies the state (keyword/applied match hides like a block), ensures the `★`/`⊘` company buttons and the funnel title-filter button exist. Re-scans happen on load, `storage.onChanged`, a 2s poll, and a MutationObserver watching `childList` **and** `class` attributes (so LinkedIn re-renders re-apply within ~150ms). Applied detection is centralized (`APPLIED_SELECTORS`) with a short-badge text fallback that excludes the title subtree, so "Applied Scientist" titles and "Applied Materials" companies never false-positive.
- **Site Settings title filter** — the funnel button after each title opens a lazy single-instance prompt overlay on `document.body`, prefilled with the job title; confirming trims and sends `site-settings:addTitleKeyword`, which the background dedupes case-insensitively, persists, and confirms with a toast (`storage.onChanged` then re-scans every tab). Enter/Escape/overlay-click dismiss the prompt; teardown removes it along with the buttons.
- **Site Settings block** — block is applied as a class *and* inline `display:none !important` because LinkedIn's framework rewrites `className` on result-card nodes during selection/recycling; a class-only hide would be silently dropped. Buttons stop event propagation so clicks never reach the card's own navigation handler.
- **Site Settings toggle** — clicking a button sends `site-settings:setCompanyState`; the background persists the site's lists and (for block) calls `notify(tab, title, msg, action)` with an Undo action. `storage.onChanged` then broadcasts the change to every open tab. Block and highlight are mutually exclusive per company.
- **Site Settings Glassdoor rating** — gated by `sites.linkedin.showGlassdoorRatings` (default `false`); when off, the content side never issues `getRatings` and the background short-circuits. When on, the content script debounces (250 ms) the unique on-screen company names and sends a single `site-settings:glassdoor:getRatings` batch to the background. The background returns cache hits from `browser.storage.local` (`jtk-site-settings-glassdoor`) synchronously and queues misses through a serial typeahead → BFF → Overview-HTML pipeline against `api.glassdoor.com` (the API host is not behind Cloudflare — no cookie, no cold-start). Fetches are throttled (≥ 2 s gap, 15 per session). Cached for 90 d on success, 7 d on failure; `schemaVersion` lets future fetcher changes evict stale entries automatically. The badge has three states: success (`★ 4.4`, click opens the Glassdoor profile in a new tab), retrying (CSS-only spinner while a `?`-click retry is in flight), and failed (`?`, click to retry). Hidden cards (blocked / keyword / applied) are skipped and have their badge removed. Failures and "no reviews" both render as `?`; the user clicks to retry via `site-settings:glassdoor:retryRating`, which evicts the cache entry and re-queues the fetch. Toggle off, module deactivation, or navigating away tears down every `.jtk-ss-gd` wrapper.
- **Site Settings people-search company** — gated by `sites.linkedin.showPeopleSearchCompany` (default `false`); when off, the content side never inserts `.jtk-ss-ppl` wrappers and never issues `getCompany`. When on, the people driver finds every `role="listitem"` card, extracts the profile URL (the card's first `/in/<vanity>/` link), the title row, and the text column, and inserts a `.jtk-ss-ppl` wrapper under the title row (with the same class set as the location row, so it looks native) initialized in the `…` pending state. Each wrapper is registered with an `IntersectionObserver` (1% visibility threshold) so a `site-settings:people:getCompany { vanity, profileUrl, name }` request fires the first time the card scrolls into view — off-screen results never trigger fetches. The background re-reads `showPeopleSearchCompany` on every request and short-circuits to `{ ok: false, reason: "toggle_off" }` when off. On a cache miss the background enqueues a serial (≥ 2 s gap) `fetch()` against the profile URL with the user's `cookies` attached (`credentials: "include"`), parses the company `<p>` from the response's top card (the line identifiable by the `_08b5ea62` class; the top card is server-rendered, so it's present in the `fetch()` body — no client-side wait needed), caches the result in `browser.storage.local` under `jtk-site-settings-people` keyed by lowercased vanity (7 d on success, 1 h on failure; `schemaVersion` lets future fetcher changes evict stale entries), and broadcasts `site-settings:people:companyResolved` to the originating tab. The content side updates its in-memory map and re-renders the line: `ok:true` replaces `…` with the company name; `ok:false` (private profile, 404, auth wall, parse miss) **removes the wrapper** so a permanent "—" never appears (the next scan will retry after the failure TTL). A cache hit (fresh entry) returns synchronously without a fetch. Toggle off, module deactivation, or navigating away removes every `.jtk-ss-ppl` wrapper; the Clear-cache button on the options page fires `site-settings:people:clearCache` to drop the local cache key.
