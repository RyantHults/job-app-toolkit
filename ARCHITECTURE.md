# Architecture

Firefox WebExtension (Manifest V2). Two modules ship today (**Form Filler** and **Site Settings**); the framework supports more.

## Layout

- `core/` — framework.
  - `storage.js` — per-module store under one `jobAppToolkit` sync key, active flags, legacy migration. Bulky per-module payloads live in `browser.storage.local` instead (form-filler AI background entries, API key) because the sync quota is a hard 100 KiB.
  - `background.js` — module registry, shared context-menu root, message router (passes the real `sender` to modules), toast relay, last-web-tab tracker, activity broadcast.
  - `popup.{js,html,css}` — module list, activity toggle, quick actions, open-options.
  - `ui.js` — shared status line + confirm/prompt modal for extension pages.
  - `content.js` — content-side runtime exposed as `window.jobAppToolkit.content`: module-active cache (`isModuleActive`/`refreshActive`) and a `showToast(text, action)` that renders an optional action button. Every content script loads it first.
- `modules/<id>/` — self-contained modules registered via `window.jobAppToolkit.registerModule(...)`.
  - `modules/form-filler/content.js` — field discovery, 3-pass matching (exact → contains → word overlap), normalization, native value setters, checkbox/select handling, same-origin iframe walk, capture/collect/fill handlers, in-page toast, and save/up-arrow per-field buttons (add to profile / fill from profile) rendered only on whitelisted hosts (full teardown when the module is off or the host isn't whitelisted). Buttons render into the top document and any unmarked same-origin iframe; the whitelist matches an entry's exact hostname or any subdomain; a 2s poll re-scans for late-loading form iframes. The AI flow reuses this field machinery: `form-filler:getAIFieldInfo` captures a right-clicked field's label/maxlength/type, `form-filler:fillAIField` writes the AI answer back through the same native value setters, and `form-filler:aiSpinner` toggles a field-anchored loading ring (its own `<style id="jtk-form-filler-spinner-styles">`, `position:fixed` from `getBoundingClientRect()`, rAF/scroll/resize tracking) while an answer is pending. The spinner's lifecycle is purely message-driven — teardown() deliberately never touches it, because the AI flow also runs on non-whitelisted pages where teardown fires every 2s. A max-age watchdog (`SPINNER_MAX_AGE_MS` = 100s) self-hides the ring if the hide message can never arrive (e.g. the background died mid-flight); the background normally hides it first at its 90s flow deadline.
  - `modules/form-filler/background.js` — module registration: popup quick actions, the `form-filler:addField` handler, cross-frame collect/fill orchestration with force-pass fallback, and a page-level context menu (Add all fields / Fill page — the per-field menu items moved to the in-page buttons). Filling a page (popup, options, or menu) auto-adds its domain to the `whitelist`. An "Answer with AI" menu item (editable contexts) captures the field, builds a prompt from the stored AI background entries, calls the configured OpenAI-compatible `chat/completions` endpoint, self-checks the answer (deterministic rules, then an LLM judge) with one corrective retry, truncates to the field's maxlength and fills it back in, with a spinner on the field via `form-filler:aiSpinner`. The whole AI section runs under a flow deadline (`aiTimeouts` — 60s per call, 90s total) that aborts in-flight calls through a shared `AbortController` and toasts a distinct "timed out" message (per-call endpoint abort vs flow deadline); the spinner never sits through the full worst case.
  - `modules/form-filler/options.{js,html,css}` — profile management, search with %-match highlighting, and the "Button sites" whitelist editor (`whitelist` array of hostnames). Also carries the AI answers config (endpoint, model, editable agent instructions — blank falls back to the built-in default — and the API key — kept in `browser.storage.local`, never synced) and the AI background entry editor (`aiContext` array of `{ title, body }`, also in `browser.storage.local`).
  - `modules/site-settings/content.js` — page adapter (currently LinkedIn) + driver: scan job cards, block/highlight cards, hide cards matching title keywords or marked applied, inject per-company buttons and per-title filter buttons (with an in-page prompt for adding title keywords), mutation observation, re-render-resilient hide.
  - `modules/site-settings/background.js` — `setCompanyState` / `addTitleKeyword` / `undoBlock` handlers; block raises a toast with an Undo action, keyword adds raise a plain confirmation toast.
  - `modules/site-settings/options.{js,html,css}` — global toggle, Blocked/Highlighted company lists, the hidden-title-keywords list, and the hide-applied switch.
- `manifest.json` — MV2, permissions `storage`, `contextMenus`, `tabs`, `<all_urls>` and `unlimitedStorage` (so `storage.local` isn't capped at the default IndexedDB quota). Content scripts run `all_frames` at `document_idle`; background loads `storage.js` → `background.js` → module background scripts. Site Settings content scripts are `["core/content.js", "modules/site-settings/content.js"]` for LinkedIn.

## Messaging

- `jtk:*` — core-reserved (getModules, setModuleActive, runQuickAction, openOptions, showToast, moduleActivityChanged).
- `<moduleId>:*` — dispatched to the owning module's `handleMessage(message, sender, moduleApi())`; `sender` carries the originating tab/frame.
- Context-menu clicks are dispatched to every module, which filters its own menu ids.
- `jtk:showToast` accepts an optional `action = { type, label, payload }`; clicking the action button sends `type` back to the background (used by Site Settings' Undo).

## Key flows

- **Fill page / collect** — background gets frame ids via `tabs.getAllFrames`, sends per-frame messages, dedupes/merges results. When nothing responds, a "force" pass asks the top frame to walk even `data-jtk-injected` same-origin iframes directly.
- **Fill field / add field** — the in-page `★` button sends `form-filler:addField` with `{ name, value, fieldLabel }`; the background merges it into the active profile and the content script toasts the result (the "Add Current Field" popup quick action still resolves the focused field across frames via `getFocusedField` → `document.activeElement` + `findFieldNear`). Per-field buttons are inserted after each fillable field (tracked in a WeakMap so re-scans update state instead of rebuilding; each document gets its own stylesheet) only when the module is active **and** the hostname (or a parent of it) is in the `whitelist`; the same-origin walk renders them into unmarked form iframes that lack their own content script. `⊘` matches the field against the active profile locally and fills unconditionally — overwriting, by design.
- **Answer with AI** — the module's "Answer with AI" menu item (editable contexts only) sends `form-filler:getAIFieldInfo` to the right-clicked frame: the field's label/name becomes the question, its `maxlength` a constraint. The background guards on a configured key/endpoint/model/background, toasts "Asking AI…", signals the spinner (`form-filler:aiSpinner` on the target field), then POSTs the prompt to the endpoint (`Authorization: Bearer`, `max_tokens`, 60s abort); the system message is the options-page "Instructions for the AI agent", blanking it restores the built-in default. The answer is then self-checked before filling: deterministic rules (empty, over `maxlength`, newlines in a single-line field) via `runDeterministicChecks`, and when clean, a strict LLM judge (`JUDGE_SYSTEM`, 120 `max_tokens`, temperature 0, fail-open on error) via `buildJudgeMessages`/`parseJudgeResult`. Any failure triggers exactly one corrective retry that re-sends the prompt with the prior answer as an assistant turn and the critique as a follow-up user message (`buildRetryMessages`); the retry is re-checked deterministically (warn-only). The answer is then truncated to the field's maxlength (word-boundary cut) and written back via `form-filler:fillAIField`, which re-resolves the same field and overwrites by design; the spinner is hidden on every terminal path (API error, fill failure, success). The whole AI section runs under a flow deadline (`aiTimeouts`: 60s per call, 90s total) that aborts in-flight calls through a shared `AbortController`; the failure toast distinguishes a flow deadline ("AI answer timed out after 90 seconds.") from a per-call endpoint abort ("the endpoint did not respond"). The API key and the AI background entries live in `browser.storage.local` (never synced — the sync quota is a fixed 100 KiB); endpoint/model are synced and edited on the options page.
- **Matching** — candidates in priority order (name, id, placeholder, linked/parent label, aria-label/-labelledby, header-like walk). Passes: exact identity, then contains, then word overlap (≥2 shared significant words).
- **Content script** — no-ops unless the module is active (cached flag refreshed on load + broadcast). Marks each document `data-jtk-injected="1"` so the iframe walk skips frames reached by per-frame messaging.
- **Site Settings scan** — the driver selects a page adapter (`currentAdapter()`), finds cards via adapter selectors, and per card: matches the company name against the site's blocked/highlighted lists, the title against `titleBlockedKeywords`, and (when `hideApplied` is on) the card against applied-markers detection; applies the state (keyword/applied match hides like a block), ensures the `★`/`⊘` company buttons and the funnel title-filter button exist. Re-scans happen on load, `storage.onChanged`, a 2s poll, and a MutationObserver watching `childList` **and** `class` attributes (so LinkedIn re-renders re-apply within ~150ms). Applied detection is centralized (`APPLIED_SELECTORS`) with a short-badge text fallback that excludes the title subtree, so "Applied Scientist" titles and "Applied Materials" companies never false-positive.
- **Site Settings title filter** — the funnel button after each title opens a lazy single-instance prompt overlay on `document.body`, prefilled with the job title; confirming trims and sends `site-settings:addTitleKeyword`, which the background dedupes case-insensitively, persists, and confirms with a toast (`storage.onChanged` then re-scans every tab). Enter/Escape/overlay-click dismiss the prompt; teardown removes it along with the buttons.
- **Site Settings block** — block is applied as a class *and* inline `display:none !important` because LinkedIn's framework rewrites `className` on result-card nodes during selection/recycling; a class-only hide would be silently dropped. Buttons stop event propagation so clicks never reach the card's own navigation handler.
- **Site Settings toggle** — clicking a button sends `site-settings:setCompanyState`; the background persists the site's lists and (for block) calls `notify(tab, title, msg, action)` with an Undo action. `storage.onChanged` then broadcasts the change to every open tab. Block and highlight are mutually exclusive per company.
